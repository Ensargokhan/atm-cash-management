# ATM Cash Management Backend

Cash management backend for a bank's ATM network: cassette configuration, cash loading, two-step withdrawals
(quote → confirm) with optimal note selection, deposits, reconciliation with four-eyes approval, an immutable
cassette movement ledger, reporting and low-cash alerts.

**Stack:** .NET 8 · ASP.NET Core Web API · EF Core 8 (code-first, migrations) · SQL Server 2022 · MediatR (CQRS) ·
FluentValidation · AutoMapper · xUnit · Testcontainers · Docker Compose

---

## 1. How to run

### With Docker (API + database)

```bash
docker compose up --build
```

| What | URL |
|---|---|
| Swagger UI | http://localhost:8080/swagger |
| Health check | http://localhost:8080/health |

Migrations run automatically on startup, and the API retries until SQL Server is ready. Ports and secrets can be
overridden with the `API_PORT`, `DB_PORT`, `SA_PASSWORD` and `CARD_HASH_PEPPER` environment variables.

### Locally (API from the IDE, database in Docker)

```bash
docker compose up -d db
dotnet run --project src/AtmCash.Api        # http://localhost:8080/swagger
```

### Tests

```bash
dotnet test
```

* **Unit tests** (`tests/AtmCash.UnitTests`, 71 tests) do not need any infrastructure. They include the 8
  acceptance tests from B3 (`Withdrawals/NoteSelectorAcceptanceTests.cs`).
* **Integration tests** (`tests/AtmCash.IntegrationTests`, 20 tests) start a real SQL Server 2022 container with
  Testcontainers, so **Docker must be running**. They host the full API with `WebApplicationFactory` and cover
  parallel quotes (B6), concurrent idempotent confirms, quote expiry, daily limits across ATMs, four-eyes approval,
  the X-User rules, the audit history, the outbox and the full end-to-end scenario.

### Postman

Import `postman/AtmCash.postman_collection.json` and `postman/AtmCash.local.postman_environment.json`, then run the
collection in order with the Collection Runner. It can also be run from the command line:

```bash
npx newman run postman/AtmCash.postman_collection.json -e postman/AtmCash.local.postman_environment.json
```

The scenario is: create ATM → configure cassettes → load cash → put in service → request quote → confirm → deposit →
switch to maintenance → reconcile → report. It has a few extra steps that show the idempotent replay, four-eyes
approval, the ledger consistency check and the ATM status history. Each request has test assertions (42 in total).
The collection is generated by `postman/generate_collection.py`.

## 2. Architecture

```
src/
  AtmCash.Domain          Aggregates and business rules. No framework dependencies.
                          Atm (+ Cassette), Quote, Reconciliation, ExchangeRate, CassetteMovement, NoteSelector,
                          AtmStatusChange, ExchangeRateChange (audit history)
  AtmCash.Application     CQRS use cases (MediatR commands/queries + handlers), FluentValidation validators,
                          pipeline behaviors, repository/unit-of-work interfaces, DTOs, AutoMapper profile
  AtmCash.Infrastructure  EF Core DbContext (= unit of work), configurations, migrations, generic + specific
                          repositories, SQL Server locks, idempotency store, HMAC card hasher, outbox, hosted services
  AtmCash.Api             Controllers, ProblemDetails error handling, Swagger, health check
tests/
  AtmCash.UnitTests        Domain rules, note selection, card hashing
  AtmCash.IntegrationTests Real SQL Server (Testcontainers) + full HTTP pipeline
```

Dependencies point inwards: Api → Infrastructure → Application → Domain.

### Request pipeline

```
Controller ──► MediatR
                 LoggingBehavior        timing / failures
                 CurrentUserBehavior    IRequiresUser only: valid X-User required → 400
                 ValidationBehavior     FluentValidation → 400
                 TransactionBehavior    commands only: BEGIN TRAN … SaveChanges … COMMIT
                 IdempotencyBehavior    IIdempotentCommand only (runs inside the transaction)
                   Handler ──► Repository.GetForUpdateAsync (row lock) ──► Domain aggregate method
                                                                          (validates, changes balances,
                                                                           records movements + domain events)
              AppDbContext.SaveChangesAsync: balances + ledger movements + outbox rows in ONE transaction
```

Commands and queries are separated (`ICommand<T>` / `IQuery<T>`). Only commands open a transaction.

### Key design decisions

#### Optimal note selection (B3): dynamic programming, not greedy

Picking the largest note first fails when stock is limited. For example, 160 from {50×3, 20×10}: greedy takes 50×3
and is left with 10, while 50×2 + 20×3 pays exactly. This is the *bounded change-making* problem, and
`Domain/Withdrawals/NoteSelector.cs` solves it with DP:

* All denominations are multiples of their GCD (10), so amounts are indexed in units of 10.
* `best[s]` holds the fewest notes that pay exactly `s`. Each denomination `d` with `c` notes is folded in with
  `best'[s] = min_{k≤c} best[s − k·d] + k`. The chosen `k` is stored per denomination so the breakdown can be
  rebuilt for any amount.
* One pass gives the exact amount, the **lower** alternative (largest payable amount below the request) and the
  **upper** alternative (smallest payable amount above it, only if it is within the remaining daily limit). Each
  alternative also uses the fewest notes.
* Size is bounded by the hardware: at most 4 cassettes × 100 notes, which is ≤ 20,000 amount states × ≤ 400
  notes. A full ATM is solved in milliseconds. Ties are broken in favour of larger denominations.

#### Concurrency (B6): one lock per ATM

Every operation that changes an ATM's cash (quote, confirm, cancel, deposit, load, reconcile, state change) starts
by loading the ATM with `SELECT … WITH (UPDLOCK, ROWLOCK)` inside the command's transaction
(`AtmRepository.GetForUpdateAsync`). Operations on the same ATM are therefore serialised. The second request waits,
then reads the balances and reservations that the first one committed, so a physical note can never be reserved
twice. Different ATMs never block each other.

* **Why pessimistic rather than optimistic:** a single ATM sees a handful of operations per minute, so waiting
  costs nothing. Optimistic concurrency (rowversion and retry) would push retry logic to every caller for no
  benefit. The lock is also visible in one place and easy to reason about.
* **Daily limit across ATMs:** the same card can be quoted on two ATMs at once, and there is no single row to lock
  for that. Quote creation therefore also takes an application lock (`sp_getapplock`) named after the card hash and
  currency.
* **Lock order** is always ATM, then card (or idempotency key, then ATM), so the locks cannot deadlock.
* **Database safety net:** check constraints keep `0 ≤ ReservedCount ≤ Count ≤ Capacity`.
* **Proof:** `ConcurrencyTests` sends 20 parallel quotes for 300 TRY against 10 notes of 100. Exactly 10 notes get
  reserved (three exact quotes plus one 100 lower alternative) and the other 16 requests get `INSUFFICIENT_CASH`.
  As a negative control, removing the `UPDLOCK` makes the test fail with 60 notes reserved (lost updates).

#### Quote and confirm (B4)

* A quote stores the offered options and the **reservation per cassette**. When both a lower and an upper
  alternative are offered, it reserves, per denomination, the larger of the two counts, so either one can be
  confirmed. On confirm, the chosen option's notes are dispensed (`WITHDRAWAL`) and the remainder is released
  (`RESERVATION_RELEASE`).
* **Expiry after 60 s** happens in two ways:
  1. A hosted service (`QuoteExpiryService`) releases expired reservations every 5 s.
  2. Every new quote on an ATM first expires that ATM's stale quotes, so stale reservations never block a customer.
  A confirm after expiry is rejected with `QUOTE_EXPIRED`. Expired quotes also stop counting towards the daily
  limit the moment they expire.
* Time comes from `TimeProvider`, so tests use a `FakeTimeProvider` and do not have to wait 60 s.

#### Idempotency (B4)

`ConfirmQuoteCommand` implements `IIdempotentCommand`. `IdempotencyBehavior` runs **inside** the command's
transaction and does three things:

1. Takes an `sp_getapplock` on the key, so concurrent retries of the same key are serialised.
2. Returns the stored response if the key was already used. If the same key comes with a different payload, it
   rejects the request with `IDEMPOTENCY_KEY_REUSED` (422).
3. Otherwise runs the handler and stores the response **in the same transaction** as the debit.

A replayed response carries an **`Idempotent-Replayed: true`** header, so the client can tell a retry from a new
execution. The behavior only sets a per-request flag (`IdempotencyContext`); the API layer turns it into the header,
because the Application layer does not know about HTTP.

Because of step 3, a stored result always means "executed exactly once", and a crash rolls back both the debit and
the record. A confirm with a *different* key on an already confirmed quote is rejected by the domain
(`QUOTE_NOT_PENDING`), so cash can never be debited twice. The test sends 8 concurrent confirms with the same key and
checks that all 8 get the same body and that there is exactly one `WITHDRAWAL` movement.

#### Movement ledger (B8)

* Each cassette keeps two balances: physical `Count` and `ReservedCount`. Every movement stores its signed effect
  on both (`CountDelta`, `ReservedDelta`), so both balances can be rebuilt by summation:

  | Movement | CountDelta | ReservedDelta |
  |---|---|---|
  | LOAD / DEPOSIT | +n | 0 |
  | UNLOAD | −n | 0 |
  | RESERVATION | 0 | +n |
  | RESERVATION_RELEASE | 0 | −n |
  | WITHDRAWAL | −n | −n |
  | RECONCILIATION_ADJUSTMENT | ±n | 0 |

* Movements are created **only by the `Atm` aggregate**, in the same method that changes the balance.
  `AppDbContext.SaveChangesAsync` inserts them with the balances, so the two cannot diverge.
* Immutability is enforced at three levels: private setters in the domain, a `SaveChanges` guard, and an
  `INSTEAD OF UPDATE, DELETE` **trigger** in SQL Server.
* `GET /api/atms/{id}/ledger/consistency` (or `/api/ledger/consistency` for the whole network) recomputes count,
  reserved and per-currency/denomination content from the movements and lists any differences.

#### Audit history

* **ATM status changes** are recorded as `AtmStatusChange` rows (from, to, `PerformedBy`, time). `Atm` changes its
  status only through one private method, `ChangeStatus`, which also queues the record, so a transition cannot
  happen without being recorded. `SaveChangesAsync` inserts the records together with the ATM, like the movements.
  The automatic transitions (Unconfigured → Configured on the first configuration, Configured → Loaded on the first
  load) are recorded with the user of that operation. `GET /api/atms/{id}/status-history` lists them.
* **Exchange rate updates** are recorded as `ExchangeRateChange` rows (currency, old rate, new rate, `ChangedBy`,
  time). `ExchangeRate.Update` returns the record and the handler stores it in the same transaction.
  `GET /api/exchange-rates/history?currency=` lists them.
* Both are append-only: private setters and a `SaveChanges` guard reject updates and deletes.

#### Other decisions

* **Card numbers (B5)** are stored as **HMAC-SHA256 with a server-side secret (pepper)**. A salted hash would make
  the same card produce different values, so the limit could not be looked up. A plain hash of a 16-digit PAN can be
  brute-forced. The pepper comes from configuration (environment variable in Docker).
* **Transactional outbox (B10):** aggregates raise `LowCashAlertRaised`, and `SaveChangesAsync` turns the event into
  an `OutboxMessages` row in the same transaction. `OutboxProcessor` (hosted service) reads rows with
  `UPDLOCK, READPAST` (safe for multiple instances), logs them and sets `SentAt`.
* **Staff identity (X-User):** commands performed by staff (configure cassettes, load, unload, put in service,
  maintenance, exchange-rate update, reconcile, approve, reject) are marked with
  `IRequiresUser`. `CurrentUserBehavior` rejects them without a user (`USER_HEADER_REQUIRED`) or with a malformed one
  (`INVALID_USER`; allowed: `a-z A-Z 0-9 . _ -`). Handlers read the user from `ICurrentUser`, which the API implements
  from the header, so moving to a token means replacing one class. Kestrel normally drops non-ASCII header values with
  an empty 400 before the request reaches the application; X-User is decoded as Latin-1 so that, for example, `Gökhan`
  gets a proper `INVALID_USER` error.
* **Four-eyes (B9):** the reconciliation stores the submitter (`X-User`). Approve and reject require a different
  user (case-insensitive). While a reconciliation is awaiting approval, the ATM refuses to return to service and
  refuses other cash operations.
* **Error model:** every error is RFC 7807 `ProblemDetails` with an `errorCode` extension and a `traceId`. Status
  codes: 400 validation/missing header, 404 not found, 409 wrong state or conflict, 422 business rule, 500
  unexpected. The codes are listed in `Domain/Common/ErrorCodes.cs`. Every endpoint documents its possible status
  codes in Swagger.
* **Patterns:** MediatR/CQRS, a generic `IRepository<T>` with specific repositories on top, `IUnitOfWork`
  (implemented by the DbContext) and AutoMapper. They were chosen to match common enterprise .NET codebases.
  Business rules stay in the domain model, and handlers only orchestrate.

## 3. Assumptions

Points that were ambiguous in the requirements, and the decision taken for each:

| # | Topic | Decision |
|---|---|---|
| 1 | "Initial setup" states | UNCONFIGURED, CONFIGURED and LOADED (the ATM has never been in service). Configuration and loading are allowed there and in MAINTENANCE. Reconciliation is allowed in CONFIGURED, LOADED and MAINTENANCE. |
| 2 | Foreign cassettes | "At least one and at most two" is read as a **requirement**: 1–2 recycling cassettes hold USD/EUR, so 2–3 hold TRY. |
| 3 | Reconfiguration | A cassette whose currency or denomination changes must be empty, so it has to be unloaded first (`CASSETTE_NOT_EMPTY`). |
| 4 | What a quote reserves | Notes for **all** offered options (per denomination, the maximum). The non-chosen part is released on confirm. |
| 5 | Limit counting of a pending quote | The **largest** offered amount counts towards the limit until the quote is confirmed (then the paid amount), cancelled or expired. |
| 6 | Request above the remaining limit | Rejected with `DAILY_LIMIT_EXCEEDED` and the remaining amount in the message. A lower alternative is not offered in its place. |
| 7 | Upper alternative and the limit | Offered only if it is ≤ the remaining limit (limit − confirmed today − pending). |
| 8 | Lower alternative | Must be greater than 0. If nothing at all is payable, the quote fails with `INSUFFICIENT_CASH`. |
| 9 | Option on confirm | `Exact`, `Lower` or `Upper`. May be omitted only when there is an exact match. |
| 10 | "Daily" | Calendar day in Europe/Istanbul (UTC+3). |
| 11 | Two cassettes with the same denomination, dispensing | Fill ratio = available / capacity. The fuller cassette is drained first, then the next. |
| 12 | Two cassettes with the same denomination, deposit | The mirror rule: notes go to the cassette with the **lower** fill ratio first. |
| 13 | Deposit currency | A deposit may mix currencies. Groups are placed in request order: matching recycling cassette, then the deposit cassette (capacity 100 notes in total), then returned with reason `CassetteFull`. |
| 14 | Reconciliation total | Σ \|difference\| × denomination × rate. Absolute values are used, so a surplus cannot hide a shortage. Approval is needed when the total is **strictly greater** than 1,000 TRY. |
| 15 | When adjustments are applied | Immediately when the total is ≤ 1,000 TRY. Otherwise only on approval; rejection applies nothing and lifts the block. |
| 16 | Reconciliation input | Every recycling cassette must be counted. For the deposit cassette, any currency/denomination not listed is counted as 0. |
| 17 | Switching to maintenance | Pending quotes are cancelled and their notes released, because reserved notes cannot be counted or unloaded. |
| 18 | Low-cash alert | Available < 10% of capacity (fewer than 10 notes). Raised once when the cassette crosses below the threshold, and again only after it has gone back above it. Not raised during initial setup. |
| 19 | X-User | Required for every staff operation: cassette configuration, cash load/unload, status changes (put in service, maintenance), exchange-rate updates and reconciliation submit/approve/reject. It is stored in the ledger (`PerformedBy`) and in the audit history. A user id is an ASCII login name (`a-z A-Z 0-9 . _ -`, at most 100 characters), not a display name. |
| 20 | Amounts | Whole currency units (integers); there are no coins. |
| 21 | Card number | 12–19 digits; spaces are ignored when hashing. |
| 22 | Idempotency scope | The key is scoped to the operation (`confirm-quote`). Only completed results are stored; a failed request is not stored and can be retried with the same key. |

## 5. Unfinished items and known limitations

* **No authentication or authorisation.** `X-User` is trusted as specified. A real system would take the user from
  a token and check roles; since the user is read through `ICurrentUser`, only the API-layer implementation changes.
* **Idempotency records are never purged.** A cleanup job with a retention period (e.g. 24 h) is needed.
* **Outbox publishing is logging only.** Delivery is at-least-once, without retry back-off or dead-letter handling.
* **Simplifications:** unload empties whole cassettes (no partial unloads), and list endpoints are not paginated.
* **AutoMapper 13.0.1** has a DoS advisory (GHSA-rvv3-g6hj-g44x) for deeply nested graphs. It is not reachable here
  (only flat entities are mapped) and is suppressed in `Directory.Build.props`; the fixed versions are commercial.

## 6. Use of AI tools

* **Tool:** Claude Code (Anthropic), used as a pair programmer.
* **What it was used for:** analysing the assignment and listing the ambiguities, setting up the solution structure,
  and writing the first version of the code, tests, Docker setup, Postman collection and this README.
* **What I checked and changed:** I went through the API by hand in Swagger and Postman, read the code and fixed
  the problems I found. I wrote the fixes myself with the AI guiding the steps, except where noted.
  * **Undocumented status codes.** A confirm with an unknown quote id returned 404, but Swagger showed it as
    "Undocumented". I reviewed every endpoint and added the missing response types (16 endpoints in 3 controllers).
  * **Confusing state messages.** Putting an ATM that is already in service back in service said
    "cannot move from InService to InService". I added clear "already in service / maintenance" messages and tests.
  * **Replays could not be told apart.** A repeated confirm with the same `Idempotency-Key` correctly returned the
    stored result, but the client could not see that it was a replay. I added the `Idempotent-Replayed: true`
    header, carried from the Application layer to the API through a scoped context.
  * **Staff identity.** Writing my name with Turkish characters in `X-User` gave an empty 400: Kestrel rejected the
    header before it reached the application, so the error model was broken. I also noticed that `X-User` was
    required for reconciliation but optional for loading and unloading cash, so the ledger could record cash
    movements with no user. I moved the user behind `ICurrentUser`, put the "user required" and format rules into one
    pipeline behavior (`CurrentUserBehavior`), made `X-User` required for all staff operations and made non-ASCII
    values get a proper `INVALID_USER` error.
  * **Audit history.** Nobody was recorded for status changes (maintenance, back in service) or exchange-rate
    updates, and the rate directly affects the 1,000 TRY approval threshold. I kept these out of the cassette ledger,
    because the ledger must stay rebuildable from balance movements, and added two history tables. The ATM status now
    changes only through one method that also writes the record. I wrote the domain part; because of time, the AI
    wrote the remaining layers, the migration and the tests, and I reviewed them.
* **Corrections made while the first version was being built:** a race in reconciliation approval (the
  reconciliation was read before the ATM lock), test expectations that did not match the rules (one Postman assertion
  and two unit tests, where the algorithm was right), pinning packages to their last MIT-licensed versions, and
  checking the concurrency test with a negative control (it fails when the lock is removed).
